Dashboard Overview với Next.js, Tailwind và ECharts

Hôm nay mình dựng trang Overview của “App Opportunity Finder” bằng dữ liệu giả, để xem bố cục và trải nghiệm trước khi có dữ liệu thật. Bài này giải thích các kiến thức đã dùng, kèm code lấy từ chính dự án.

1. Hôm nay làm gì

  • Tạo dự án Next.js 16 (TypeScript + Tailwind v4) trong thư mục frontend/.
  • Sinh dữ liệu giả: 8 lĩnh vực, 40 app, 8 công ty, ~3.000 review 1–2★ có “câu chuyện” (PDF đau vì quảng cáo, ảnh AI đau vì paywall…).
  • Dựng trang Overview: header + bộ lọc, 4 ô KPI, ① bảng xếp hạng cơ hội (có 3 thanh trượt trọng số), ② bản đồ cơ hội (scatter), ③ heatmap, ④ biểu đồ mong muốn, ⑤ bảng app đối thủ, và 2 panel bên phải.
  • Kiểm tra tự động bằng Chrome headless: không lỗi console, mọi tương tác hoạt động.

Chạy thử:

cd frontend
npm install        # lần đầu
npm run dev        # mở http://localhost:3000

Kiểm tra code trước khi nộp: npx tsc --noEmit (lỗi kiểu), npm run lint (lỗi phong cách), npm run build (build thật).

3. Kiến thức chính

3.1 Server Component và Client Component ("use client")

Trong Next.js (App Router), mọi component mặc định chạy trên server: server tạo sẵn HTML rồi gửi cho trình duyệt. Cách này nhanh, nhưng server không có chuột hay bàn phím, nên không xử lý được onClick và không giữ được useState.

Component nào cần tương tác thì ghi "use client" ở dòng đầu. Khi đó code của nó được gửi xuống trình duyệt để chạy.

src/app/page.tsx (server) → src/components/dashboard/Dashboard.tsx (client)

// page.tsx — Server Component, chỉ là cái vỏ
export default function Home() {
  return <Dashboard />;
}

// Dashboard.tsx
"use client";               // ← cần state + click nên phải là Client Component
export default function Dashboard() {
  const [filters, setFilters] = useState(DEFAULT_FILTERS);
  ...

Lỗi hay gặp: quên "use client" rồi dùng useState → Next.js báo lỗi ngay khi build. Ngược lại, đừng gắn "use client" cho mọi file “cho chắc”, vì làm vậy gửi thừa JavaScript xuống trình duyệt.

3.2 State, props và luồng dữ liệu một chiều

State (trạng thái) là dữ liệu có thể thay đổi khi người dùng tương tác: bộ lọc, trọng số, lĩnh vực đang chọn, panel đang mở. Toàn bộ state nằm ở một chỗ là Dashboard. Các component con chỉ nhận props (tham số) và gọi callback khi có sự kiện.

State ở Dashboard→ props → OpportunityTable→ người dùng bấm dòng → onSelectDomain(id)→ setSelectedDomainId→ React vẽ lại cả trang

src/components/dashboard/Dashboard.tsx

const [selectedDomainId, setSelectedDomainId] = useState<string | null>(null);

// Bấm lại đúng lĩnh vực đang chọn = bỏ chọn
const toggleDomain = useCallback((domainId: string) => {
  setSelectedDomainId((current) => (current === domainId ? null : domainId));
}, []);

<OpportunityTable onSelectDomain={toggleDomain} ... />
<OpportunityMap   onSelectDomain={toggleDomain} ... />
<PainHeatmap      onSelectDomain={toggleDomain} ... />

Nhờ cả ①, ② và ③ dùng chung một hàm toggleDomain, bấm ở chỗ nào thì toàn trang cũng lọc giống nhau. Đó là lợi ích của việc giữ state ở một nơi (“lifting state up”).

Lỗi hay gặp: mỗi component tự giữ một state selected riêng, dẫn tới bảng chọn A còn biểu đồ vẫn chọn B. Hai chỗ cần cùng một dữ liệu thì đẩy state lên component cha chung.

3.3 useMemo: dữ liệu phái sinh

Dữ liệu hiển thị (review đã lọc, điểm cơ hội…) không lưu vào state. Nó được tính ra từ state mỗi lần vẽ. useMemo giúp “nhớ” kết quả và chỉ tính lại khi đầu vào đổi. Nhờ vậy khi bạn kéo thanh trượt trọng số, React không phải lọc lại 3.000 review mà chỉ chấm điểm lại 8 lĩnh vực.

src/components/dashboard/Dashboard.tsx

const apps        = useMemo(() => filterApps(data.apps, filters.companyId), [filters.companyId]);
const reviews     = useMemo(() => filterReviews(data.reviews, apps, filters, ...), [apps, filters]);
const domainStats = useMemo(() => computeDomainStats(data, apps, reviews), [apps, reviews]);
const scored      = useMemo(() => scoreDomains(domainStats, weights), [domainStats, weights]);
//                                                                    ↑ chỉ phụ thuộc weights + stats

Lỗi hay gặp: lưu kết quả tính toán vào state rồi dùng useEffect để đồng bộ. Cách này vừa thừa vừa dễ lệch dữ liệu. Quy tắc: thứ gì tính được từ state thì đừng biến nó thành state.

3.4 TypeScript interface: “hợp đồng” dữ liệu

lib/types.ts mô tả chính xác hình dạng dữ liệu. Gõ sai tên trường là editor báo đỏ ngay. Quan trọng hơn, đây là hợp đồng giữa frontend và backend: khi làm Django, API chỉ cần trả JSON đúng hình dạng DashboardData là giao diện chạy được.

src/lib/types.ts

export interface Review {
  id: string;
  appId: string;
  score: 1 | 2;            // chỉ cho phép 1 hoặc 2 (literal type)
  date: string;            // "YYYY-MM-DD"
  lang: ReviewLang;        // "en" | "vi"
  content: string;
  painPoints: string[];    // 1 review có thể có nhiều nhãn
  wishId: string | null;   // có thể không có mong muốn
  thumbsUp: number;
}

Lỗi hay gặp: dùng any cho nhanh, làm mất hết lợi ích kiểm tra. Nếu thật sự chưa biết kiểu thì dùng unknown rồi ép kiểu có chủ đích (xem tooltip trong OpportunityMap.tsx).

3.5 Tách tính toán ra hàm thuần (pure function)

Mọi phép tính nằm trong lib/analytics.ts, không dính gì tới giao diện. Hàm thuần nghĩa là cùng đầu vào thì luôn cho cùng đầu ra, và không sửa dữ liệu gốc. Lợi ích: dễ đọc, dễ viết test, và sau này có thể chuyển nguyên logic sang Python/Django.

Ví dụ quan trọng nhất là điểm cơ hội:

src/lib/analytics.ts

const w = normalizeWeights(weights);   // 40/35/25 → 0,40/0,35/0,25 (tổng luôn = 1)
const scaleDemand = createMinMaxScaler(stats.map((s) => Math.log10(s.totalInstalls)));
...
const score = 100 * (w.demand * demandNorm
                   + w.dissatisfaction * dissatisfactionNorm
                   + w.easyFix * easyFixNorm);

Lỗi hay gặp: với min–max, lĩnh vực thấp nhất luôn bằng 0 và cao nhất luôn bằng 1, nên điểm chỉ mang tính so sánh tương đối giữa các lĩnh vực đang hiển thị. Lọc theo một công ty thì điểm sẽ thay đổi, và đó là chuyện bình thường.

3.6 Dùng thư viện không phải React (ECharts) với useRef + useEffect

ECharts không hiểu React. Nó cần một thẻ <div> thật để vẽ vào. Cách làm chuẩn gồm 3 bước:

  1. useRef lấy thẻ div thật.
  2. useEffect (chỉ chạy trên trình duyệt) gọi echarts.init, và dọn dẹp bằng dispose() khi component bị gỡ.
  3. Một useEffect khác gọi setOption mỗi khi option đổi.

src/components/charts/EChart.tsx

useEffect(() => {
  const chart = echarts.init(containerRef.current!);
  chartRef.current = chart;
  const resizeObserver = new ResizeObserver(() => chart.resize());
  resizeObserver.observe(containerRef.current!);
  return () => {               // ← hàm dọn dẹp
    resizeObserver.disconnect();
    chart.dispose();
  };
}, []);                         // [] = chỉ chạy 1 lần khi gắn vào trang

useEffect(() => {
  chartRef.current?.setOption(option, { notMerge: true });
}, [option]);

Lỗi hay gặp: quên hàm dọn dẹp, gây rò bộ nhớ hoặc cảnh báo “There is a chart instance already initialized”. Ở chế độ dev, React cố ý chạy effect 2 lần (Strict Mode) để lộ ra lỗi này sớm.

3.7 Dữ liệu giả có seed và lỗi “hydration mismatch”

Next.js render trang 2 lần: một lần trên server để tạo HTML, rồi một lần trên trình duyệt để gắn tương tác (gọi là hydration). Nếu dữ liệu giả dùng Math.random() thì 2 lần sẽ ra 2 bộ review khác nhau, và React báo lỗi hydration mismatch.

Cách giải quyết là dùng bộ sinh số ngẫu nhiên có seed: cùng seed thì luôn ra cùng dãy số. Ngày tháng cũng phải lấy từ một mốc cố định (updatedAt) thay vì new Date().

src/data/reviewGenerator.ts

function createRandom(seed: number): RandomFn {
  let state = seed >>> 0;
  return () => {
    state = (state + 0x6d2b79f5) >>> 0;
    ...                        // thuật toán mulberry32
  };
}
const random = createRandom(2026);   // lần nào chạy cũng ra đúng 3.004 review giống nhau

Lỗi hay gặp: hiển thị new Date().toLocaleString() hoặc Math.random() trực tiếp trong JSX của một component được render trên server.

Bonus: Tailwind v4 khai báo theme ngay trong CSS

Tailwind v4 không còn file tailwind.config.js. Màu được khai báo trong @theme, và mỗi biến tự sinh ra class tương ứng.

src/app/globals.css

@theme {
  --color-accent: #2a78d6;        /* → bg-accent, text-accent, border-accent/40 ... */
  --color-accent-soft: #eaf2fc;   /* → bg-accent-soft */
}

Dashboard chỉ dùng một màu nhấn (xanh dương) cho mọi thứ mang nghĩa “cơ hội”: hạng 1, vùng cơ hội trên scatter, nhóm pain point dễ sửa. Mọi thứ khác dùng màu xám. Nhờ vậy mắt người xem được dẫn thẳng tới điều quan trọng.

5. Tự kiểm tra

Câu 1. Vì sao page.tsx không cần "use client" còn Dashboard.tsx thì cần?

page.tsx chỉ trả về JSX, không có state hay sự kiện. Dashboard.tsx dùng useState và onClick, mà hai thứ này chỉ chạy được trên trình duyệt.

Câu 2. Kéo thanh “Nhu cầu” từ 40 lên 80 (hai thanh kia giữ nguyên 35 và 25). Trọng số thực tế của Nhu cầu là bao nhiêu %?

80 / (80 + 35 + 25) = 80 / 140 ≈ 57%. Hàm normalizeWeights thực hiện phép chia này.

Câu 3. Nếu bỏ Math.log10 trong điểm nhu cầu, lĩnh vực “Ghi chú/ghi âm AI” (2,6 triệu) sẽ ra sao so với hiện tại?

Nó vẫn là 0 vì đang thấp nhất. Thay đổi lớn nằm ở các lĩnh vực tầm trung. Ví dụ “Khôi phục dữ liệu” (17,5 triệu) đang có điểm nhu cầu khoảng 0,56 nhờ log. Bỏ log thì chỉ còn (17,5 − 2,6) / (76,5 − 2,6) ≈ 0,20, vì thang tuyến tính bị các lĩnh vực 76 triệu chi phối.

Bài tập 4. Thêm cột “Có quảng cáo” vào bảng ⑤ (CompetitorTable).

Gợi ý: dữ liệu đã có trong app.containsAds. Thêm một <th> trong <thead> và một <td> trong vòng .map(). Không cần sửa file nào khác, vì đó chính là lợi ích của interface đã có sẵn trường.

Bài tập 5. Thêm lựa chọn “1 tháng” vào bộ lọc thời gian.

Sửa kiểu MonthsRange trong analytics.ts thành 1 | 3 | 6 | 12, rồi thêm 1 vào mảng MONTH_OPTIONS trong HeaderBar.tsx. TypeScript sẽ chỉ cho bạn những chỗ còn lại cần sửa (nếu có).
