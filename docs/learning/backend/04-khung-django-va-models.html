Khung Django và các bảng dữ liệu

Bài backend đầu tiên. Hôm nay mình dựng “cái nhà kho” cho dữ liệu: một project Django chạy được, các bảng để lưu công ty, app, review, nhãn, cùng trang admin để xem và sửa dữ liệu bằng tay. Chưa có dữ liệu cào thật, cũng chưa có API cho extension. Hai phần đó để sang đợt sau.

1. Hôm nay làm gì

  • Chuyển git ra thư mục gốc để quản lý chung frontend/ và backend/. Backend làm trên nhánh feat/backend-django.
  • Tạo project Django (config/) và một Django app tên market.
  • Viết 9 bảng: lĩnh vực, nhóm pain, pain point, mong muốn, công ty, tài khoản developer, app, review, lần cào.
  • Nạp sẵn bộ nhãn (8 lĩnh vực, 10 pain point, 15 mong muốn, kèm từ khóa) bằng data migration.
  • Làm trang admin. Bạn sửa nhãn bằng tay thì nhãn được đánh dấu manual, để máy không ghi đè lên.
  • 13 test tự động, tất cả đều qua.

Chạy thử

cd backend
.venv/Scripts/python manage.py migrate            # tạo db.sqlite3 + nạp nhãn
.venv/Scripts/python manage.py createsuperuser    # tạo tài khoản admin (1 lần)
.venv/Scripts/python manage.py runserver          # mở http://localhost:8000/admin/
.venv/Scripts/python -m pytest                    # chạy 13 test

Mở http://localhost:8000/api/health/ sẽ thấy {"status": "ok"}. Sau này extension gọi đường dẫn này để biết Django đã bật chưa.

3. Kiến thức chính

3.1. Project và app trong Django, môi trường ảo (venv)

Project là cả “tòa nhà”: cấu hình chung, đường dẫn gốc. App là một “phòng” lo một mảng việc, ở đây là market, lo dữ liệu thị trường app. Dự án lớn có nhiều app, còn dự án mình nhỏ nên một app là đủ và dễ nắm.

venv (virtual environment) là một thư mục .venv/ chứa Python và thư viện riêng cho dự án. Nhờ vậy dự án này dùng Django 5.2 mà không đụng tới dự án khác trên máy đang dùng phiên bản khác.

backend/requirements.txt

Django>=5.2,<5.3
djangorestframework>=3.16,<3.17
django-cors-headers>=4.7,<5

Lỗi hay gặp: gõ pip install hay python trần, nên thư viện cài vào Python chung của máy thay vì .venv. Hãy luôn gọi .venv/Scripts/python ..., hoặc kích hoạt venv trước.

3.2. Model = một bảng trong database

Mỗi class trong models.py là một bảng, mỗi thuộc tính là một cột. Django tự viết câu SQL giúp bạn. Đây gọi là ORM (Object-Relational Mapping): làm việc với database bằng object Python thay vì viết SQL.

backend/market/models.py

class App(models.Model):
    id = models.CharField(primary_key=True, max_length=255)      # "com.apero.pdfreader"
    title = models.CharField(max_length=255)
    developer_account = models.ForeignKey(DeveloperAccount, on_delete=models.PROTECT, related_name="apps")
    min_installs = models.BigIntegerField()
    # 5 số lượt chấm sao, phần tử [0] là 1★, [4] là 5★
    star_histogram = models.JSONField(default=list)
    domain = models.ForeignKey(Domain, null=True, blank=True, on_delete=models.SET_NULL)

Ba loại quan hệ mình dùng:

LoạiVí dụ trong dự ánNghĩa đời thường
ForeignKey (n–1)Review → Appnhiều review thuộc về một app
ManyToManyField (n–n)Review ↔ PainPointmột review chê nhiều thứ, một thứ bị nhiều review chê
null=True trên ForeignKeyApp → Domainapp mới cào về chưa biết thuộc lĩnh vực nào

on_delete nói chuyện gì xảy ra khi bản ghi “cha” bị xóa. CASCADE: xóa app thì xóa luôn review của nó. PROTECT: không cho xóa tài khoản developer khi còn app thuộc về nó. SET_NULL: xóa lĩnh vực thì app về trạng thái “chưa có lĩnh vực”.

Lỗi hay gặp: sửa models.py rồi quên chạy makemigrations + migrate. Lúc đó database vẫn là bảng cũ, và báo lỗi kiểu “no such column”.

3.3. Chọn khóa chính khôn ngoan để chống trùng

Thường Django tự tạo cột id là số 1, 2, 3… Nhưng với review, mình dùng luôn id review của Google làm khóa chính. Vì vậy extension lỡ gửi một review hai lần (mạng lag, bấm cào lại) thì database tự nhận ra là trùng, không có bản thứ hai.

backend/market/models.py

class Review(models.Model):
    """Một review 1–2★. Khóa chính là id review của Google nên gửi lại không bị trùng."""
    id = models.CharField(primary_key=True, max_length=255)
    app = models.ForeignKey(App, on_delete=models.CASCADE, related_name="reviews")
    lang = models.CharField(max_length=2, choices=LANG_CHOICES)

Lỗi hay gặp: dùng id tự tăng rồi phải tự viết code kiểm tra trùng bằng nội dung review. Cách đó vừa chậm vừa sai, vì hai người khác nhau có thể viết cùng một câu “quá nhiều quảng cáo”.

3.4. Migration và data migration

Migration là file ghi lại “database thay đổi thế nào”, giống commit của git nhưng dành cho cấu trúc bảng. makemigrations so models.py với các migration cũ rồi sinh file mới. migrate chạy các file đó lên database.

Data migration là migration do mình tự viết để thêm dữ liệu thay vì đổi cấu trúc bảng. Mình dùng nó để nạp 8 lĩnh vực và 10 pain point. Lợi ích là database nào chạy migrate cũng có sẵn nhãn, kể cả database tạm mà pytest tạo ra khi chạy test.

backend/market/migrations/0002_seed_taxonomy.py

def seed_taxonomy(apps, schema_editor):
    # Dùng apps.get_model thay vì import model trực tiếp: migration phải chạy với
    # "phiên bản bảng" tại thời điểm migration này, không phải bản mới nhất trong models.py.
    Domain = apps.get_model("market", "Domain")
    for order, item in enumerate(DOMAINS):
        Domain.objects.create(id=item["id"], name=item["name"], keywords=item["keywords"], order=order)

Lỗi hay gặp: viết from market.models import Domain trong migration. Hôm nay vẫn chạy, nhưng vài tháng sau bạn thêm cột mới vào Domain thì migration cũ này sẽ hỏng khi chạy trên máy mới.

3.5. Trang admin và quy tắc “sửa tay thì máy không được ghi đè”

Django tặng sẵn trang /admin/ để xem, thêm, sửa, xóa dữ liệu. Mình chỉ cần khai báo bảng nào hiện cột gì, lọc theo gì. Mình còn “chen” vào lúc bấm Lưu: nếu bạn đổi lĩnh vực của app thì đánh dấu domain_source = "manual". Sau này lệnh gắn nhãn tự động thấy manual sẽ bỏ qua app đó, nên công sửa tay của bạn không bị mất.

backend/market/admin.py

@admin.register(App)
class AppAdmin(admin.ModelAdmin):
    list_filter = [MissingDomainFilter, "domain", "skipped_reason"]

    def save_model(self, request, obj, form, change):
        # form.changed_data = danh sách tên trường người dùng vừa sửa trong form
        if "domain" in form.changed_data:
            obj.domain_source = "manual"
        super().save_model(request, obj, form, change)

Lỗi hay gặp: quên gọi super().save_model(...) ở cuối. Khi đó mọi thứ trông như đã lưu nhưng thực ra không có gì được ghi vào database.

3.6. Hàm thuần trong services/ và chuyện chia cho 0

Hàm thuần là hàm chỉ nhận vào rồi trả ra, không đọc database, không sửa gì bên ngoài. Hàm như vậy test rất dễ, không cần dựng dữ liệu. Mình gom chúng vào market/services/, tách khỏi view, giống như frontend gom tính toán vào lib/analytics.ts.

backend/market/services/stars.py

def low_star_ratio(histogram: list[int]) -> float:
    """Tỉ lệ lượt chấm 1–2★ trên tổng. Ví dụ [20, 10, 10, 20, 40] -> 0.3."""
    if len(histogram) != STAR_LEVELS:
        return 0.0
    total = sum(histogram)
    if total == 0:
        return 0.0
    return round((histogram[0] + histogram[1]) / total, 4)

Để ý cách viết return sớm: loại các trường hợp xấu trước, nên dòng tính toán chính ở cuối không phải lồng trong if nào.

Lỗi hay gặp: app mới lên chưa ai chấm sao, sum = 0, chương trình dừng với ZeroDivisionError giữa lúc đang cào. Luôn hỏi “nếu dữ liệu rỗng thì sao?”.

3.7. pytest, fixture “nhà máy” và TDD

Mình viết test trước, code sau (TDD). Chạy test thấy đỏ (vì code chưa có), viết code, chạy lại thấy xanh. Thấy đỏ trước là bằng chứng test thật sự kiểm tra được điều gì đó.

Fixture là thứ pytest tự chuẩn bị rồi đưa vào test qua tên tham số. Fixture db cho phép test dùng database tạm. make_app là fixture “nhà máy” do mình viết: tạo app với giá trị mặc định hợp lệ, test chỉ cần đổi đúng chỗ nó quan tâm.

backend/tests/test_models.py

def test_scope(make_app, make_developer):
    assert is_in_scope(make_app()) is True

    foreign = make_developer(play_developer_id="adobe", status="foreign", company=None)
    assert is_in_scope(make_app(id="com.adobe.reader", developer_account=foreign)) is False

Lỗi hay gặp: mỗi test tự tạo đủ 15 trường của app. Khi thêm một cột bắt buộc mới, bạn phải sửa 30 test. Có “nhà máy” thì chỉ sửa một chỗ trong conftest.py.

3.8. API đầu tiên với DRF, CORS và CSRF

Django REST Framework (DRF) giúp viết API trả JSON gọn hơn Django thuần. Endpoint đầu tiên chỉ có 3 dòng:

backend/market/api/views.py

@api_view(["GET"])
def health(request: Request) -> Response:
    """Trả {"status": "ok"} — extension gọi để biết Django đã bật hay chưa."""
    return Response({"status": "ok"})
  • CORS: trình duyệt mặc định chặn trang localhost:3000 gọi sang localhost:8000, vì khác “nguồn gốc” (origin). Thư viện django-cors-headers báo cho trình duyệt rằng hai nguồn này được phép gọi nhau.
  • CSRF: Django mặc định đòi một token chống giả mạo cho mọi request POST. Mình tắt đăng nhập trong DRF, nên DRF không đòi token, và extension POST dữ liệu được. Cách này chỉ an toàn vì backend chạy trên máy cá nhân.

Lỗi hay gặp: đặt CorsMiddleware dưới CommonMiddleware. Khi đó header CORS không kịp gắn vào response, và trình duyệt vẫn báo lỗi CORS dù bạn đã cài thư viện.

5. Tự kiểm tra

1. Bạn thêm cột icon_url vào model App. Cần chạy những lệnh gì để database có cột đó?

.venv/Scripts/python manage.py makemigrations (sinh file migration 0003_...) rồi .venv/Scripts/python manage.py migrate (áp vào database). Nhớ commit cả file migration mới.

2. Vì sao Review.id lấy id của Google mà không để Django tự đánh số 1, 2, 3?

Để chống trùng: gửi lại cùng review thì khóa chính trùng, database tự biết đã có. Nếu tự đánh số thì mỗi lần gửi lại sẽ thành một dòng mới.

3. Trong admin bạn đổi lĩnh vực của app “Flashlight Pro” từ trống sang “Launcher”. Lệnh gắn nhãn tự động chạy sau đó có đổi lại không? Vì sao?

Không. save_model trong AppAdmin đã đặt domain_source = "manual", và lệnh tự động (làm ở đợt sau) bỏ qua mọi app có nguồn manual.

4. Viết thêm một test: app có biểu đồ sao [0, 0, 0, 0, 10] thì low_star_ratio bằng bao nhiêu? 
def test_low_star_ratio_all_five_star():
    assert low_star_ratio([0, 0, 0, 0, 10]) == 0.0

Tổng là 10 (khác 0), lượt 1–2★ là 0, nên 0 / 10 = 0.0. Bạn đặt test vào tests/test_models.py rồi chạy .venv/Scripts/python -m pytest.

5. Một app do Adobe đăng. Cần những điều kiện gì để is_in_scope trả True?

Tài khoản developer phải có status = "assigned", có company, và company.is_vietnamese = True. Adobe không phải công ty Việt nên sẽ là False. App vẫn được lưu, chỉ là không hiện trên dashboard.
