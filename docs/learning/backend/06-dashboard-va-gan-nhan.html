Dashboard API và gắn nhãn bằng từ khóa

Đợt 2 làm “cửa nhập hàng”. Đợt 3 làm hai việc còn lại để có đường đi trọn vẹn từ cào tới dashboard: (1) lệnh label_data đọc review và tự gắn nhãn “chê quảng cáo”, “hay văng app”… bằng từ khóa; (2) GET /api/dashboard/ trả JSON đúng hình dạng mà Next.js đang dùng với dữ liệu giả.

1. Hôm nay làm gì

Luồng dữ liệu giờ đã đủ các khúc (chỉ còn thiếu extension ở đầu và frontend gọi API ở cuối):

extension ──POST──▶ /api/ingest/app/, /api/ingest/reviews/     (đợt 2)
                         │
               manage.py label_data                                (đợt 3)
                         │   gán domain cho app, pain point + mong muốn cho review
                         ▼
Next.js  ◀──GET─── /api/dashboard/                                  (đợt 3)

Chạy test (90 test, đều xanh) và các lệnh mới:

cd backend
.venv/Scripts/python -m pytest
.venv/Scripts/python manage.py label_data            # gắn nhãn phần chưa gắn
.venv/Scripts/python manage.py label_data --relabel  # gắn lại tất cả (trừ nhãn sửa tay)
.venv/Scripts/python manage.py sample_labels --n 50  # in 50 review để chấm đúng/sai
.venv/Scripts/python manage.py runserver
# mở http://localhost:8000/api/dashboard/?include_foreign=1

Đã thử tay cả đường đi: gửi 1 app + 3 review bằng curl → gửi lại thì nhận duplicates: 3 → label_data gán lĩnh vực pdf và nhãn ads, crash, paywall + mong muốn offline → dashboard hiện đủ (chỉ khi ?include_foreign=1, vì tài khoản developer đó chưa được gán công ty Việt).

Trên Git Bash ở Windows, gõ tiếng Việt thẳng trong curl -d '...' sẽ bị sai mã hóa (lỗi “can't decode byte”). Ghi JSON ra file UTF-8 rồi dùng --data-binary @file.json.

3. Kiến thức chính

3.1. API là một “hợp đồng”: khớp từng tên trường với types.ts

Frontend đã chạy với dữ liệu giả có hình dạng DashboardData. Nếu backend trả đúng hình dạng đó thì frontend không phải sửa gì. Nên mình viết hàm _serialize_app chép tay từng trường (Python dùng snake_case, JSON dùng camelCase), và test kiểm tập khóa ở mọi cấp. Lỡ gõ offersIap thay vì offersIAP là test đỏ ngay.

market/services/dashboard.py

def _serialize_app(app: App) -> dict:
    histogram = app.star_histogram
    has_histogram = len(histogram) >= 2
    return {
        "id": app.id,
        "companyId": _company_id_of(app),
        "lowStarRatio": app.low_star_ratio,
        "oneStarRatings": histogram[0] if has_histogram else 0,
        "twoStarRatings": histogram[1] if has_histogram else 0,
        "offersIAP": app.offers_iap,
        ...
    }

Lỗi hay gặp: test chỉ kiểm “có trường X” mà không kiểm “không có trường thừa”. Dùng set(keys) == EXPECTED_KEYS để bắt cả hai.

3.2. Lỗi N+1 và cách đếm số truy vấn trong test

“N+1” là khi bạn lấy 100 app bằng 1 truy vấn, rồi trong vòng lặp hỏi app.developer_account.company — mỗi app thêm 1–2 truy vấn nữa. Code vẫn đúng, chỉ chậm dần khi dữ liệu nhiều, nên rất khó thấy. select_related gộp bằng JOIN ngay từ đầu. Để chắc chắn, test dùng fixture django_assert_max_num_queries: 5 app × 5 review mà quá 12 truy vấn là đỏ.

market/services/dashboard.py · tests/test_dashboard.py

candidates = App.objects.filter(skipped_reason="", domain__isnull=False).select_related(
    "developer_account__company"   # __ đi xuyên quan hệ: app → developer → company
)

with django_assert_max_num_queries(12):
    data = get_dashboard(client)

Lỗi hay gặp: select_related chỉ dùng cho ForeignKey (quan hệ “một”). Quan hệ “nhiều” (ManyToMany như pain_points) phải dùng prefetch_related hoặc cách ở mục 3.3.

3.3. Đọc thẳng bảng trung gian của ManyToMany

Quan hệ nhiều-nhiều review ↔ pain point được Django lưu trong một bảng ẩn có 2 cột review_id, painpoint_id. Truy cập bảng đó bằng Review.pain_points.through. Ở dashboard, mình đọc bảng này một lần rồi gom thành dict {review_id: [pain_id, ...]}. Lý do không dùng prefetch_related: nó nhét id của mọi review vào một câu IN (...), mà SQLite giới hạn khoảng 32.000 tham số/câu — 40 app × 1.000 review là vượt.

market/services/dashboard.py — _pain_point_ids_by_review

links = (
    Review.pain_points.through.objects.filter(review__app_id__in=app_ids, review__labeled_at__isnull=False)
    .order_by("painpoint__order")
    .values_list("review_id", "painpoint_id")
)
pain_ids_by_review: dict[str, list[str]] = defaultdict(list)
for review_id, pain_point_id in links:
    pain_ids_by_review[review_id].append(pain_point_id)

Lỗi hay gặp: dùng dict thường rồi gọi d[review_id] cho review không có nhãn nào → KeyError. defaultdict(list) tự trả list rỗng.

3.4. Chuẩn hóa chữ: bỏ dấu tiếng Việt bằng Unicode NFD

Người dùng gõ “QUANG CAO QUA NHIEU”, từ khóa là “quảng cáo”. Để so được, đưa cả hai về cùng dạng: chữ thường, không dấu. Mẹo: dạng Unicode NFD tách “ả” thành “a” + “dấu hỏi” (một ký tự “combining” riêng). Bỏ các ký tự combining là hết dấu. Riêng “đ” là một chữ riêng, không tách được, nên đổi tay.

market/labeling/text.py

def normalize(text: str) -> str:
    decomposed = unicodedata.normalize("NFD", text.lower())
    without_marks = "".join(char for char in decomposed if not unicodedata.combining(char))
    without_marks = without_marks.replace("đ", "d")
    return " ".join(without_marks.split())   # gộp mọi khoảng trắng / xuống dòng thành 1 dấu cách

normalize("  Quảng   CÁO  Đầy\nmàn hình ")  # → "quang cao day man hinh"

Lỗi hay gặp: bỏ dấu làm từ khác nghĩa trùng nhau: “lỗi” và “lời” đều thành “loi”, “văng” và “vàng” đều thành “vang”. Đây là cái giá của việc khớp được chữ không dấu.

3.5. Ranh giới từ \b trong regex

Tìm chuỗi con thô thì “ads” khớp cả “downloads”. \b (word boundary) nghĩa là “ở đây phải là chỗ bắt đầu/kết thúc một từ”, nên \bads\b khớp “too many ads!” nhưng không khớp “downloads”. re.escape để từ khóa có ký tự đặc biệt như “c++” không bị hiểu là cú pháp regex.

market/labeling/text.py

pattern = r"\b" + re.escape(normalized_keyword) + r"\b"
return re.search(pattern, normalized_text) is not None

Lỗi hay gặp: quên chữ r trước chuỗi: "\b" trong Python thường là ký tự backspace, không phải ranh giới từ.

3.6. Hàm thuần tách khỏi database → dễ thay bằng AI sau này

labeling/rules.py chỉ nhận chữ + danh sách nhãn (id, keywords) và trả id nhãn. Nó không biết database là gì. Lợi ích: test chạy không cần DB (nhanh), và khi có API key thì viết label_review phiên bản LLM cùng đầu vào/đầu ra là thay được. Phần “đọc DB, ghi DB” nằm riêng ở services/labeling.py.

market/labeling/rules.py

Label = tuple[str, list[str]]   # ("ads", ["quảng cáo", "ads"])

def label_review(content, pain_labels, wish_labels) -> tuple[list[str], str | None]:
    text = normalize(content)
    pain_ids = []
    for pain_id, keywords in pain_labels:
        if matches_any(text, keywords):
            pain_ids.append(pain_id)
    ...

Chấm lĩnh vực app: từ khóa trong tên được 3 điểm, trong mô tả/thể loại được 1 điểm; lấy lĩnh vực điểm cao nhất, hòa thì lấy cái đứng trước (dùng >, không dùng >=).

Lỗi hay gặp (hạn chế của cách từ khóa): “không có quảng cáo, rất thích” vẫn bị gắn nhãn ads vì không hiểu phủ định. Vì vậy mới có lệnh sample_labels để chấm tay.

3.7. Lệnh manage.py tự viết, và ghi theo lô

Mỗi file trong market/management/commands/ là một lệnh; tên file là tên lệnh. Class Command có add_arguments (khai báo tham số như --relabel) và handle (việc cần làm). In ra bằng self.stdout.write — để test hứng được bằng StringIO.

Gắn nhãn 20.000 review mà mỗi review gọi .pain_points.set() + .save() là ~60.000 câu SQL. Ghi theo lô 500 chỉ cần 3 câu mỗi lô:

market/services/labeling.py — _label_review_batch

with transaction.atomic():
    # Xóa nhãn cũ của lô rồi ghi nhãn mới (quan trọng khi chạy --relabel)
    PainLink.objects.filter(review_id__in=batch_ids).delete()
    PainLink.objects.bulk_create(new_links)
    # bulk_update: cập nhật 3 cột cho cả lô bằng một câu UPDATE
    Review.objects.bulk_update(batch, ["wish", "labeled_at", "label_source"])

Lỗi hay gặp: dùng print() trong lệnh thay vì self.stdout.write → test không bắt được chữ in ra.

4. Vì sao chọn cách này

Quyết địnhLý doPhương án đã bỏ
Dashboard chỉ trả app có lĩnh vực + review đã gắn nhãn Không hiện dữ liệu dở dang (app “không lĩnh vực” làm vỡ biểu đồ theo lĩnh vực) Trả hết, để frontend lọc — frontend phải biết thêm quy tắc

5. Tự kiểm tra

1. Review “Too many downloads required” có bị gắn nhãn ads không? Vì sao?

Không. Từ khóa “ads” được khớp với \bads\b; trong “downloads” chữ “ads” không đứng ở ranh giới từ.

2. App “PDF Scanner”, mô tả “scan documents”. Lĩnh vực pdf có từ khóa ["pdf", "document"], scanner có ["scan", "scanner"]. Chọn lĩnh vực nào?

scanner. pdf: tên khớp “pdf” → 3 điểm; mô tả có “documents” (số nhiều) nên không khớp ranh giới từ “document”. scanner: tên khớp “scanner” (3) + mô tả khớp “scan” (1) → 4 điểm. Muốn khớp số nhiều thì thêm “documents” vào từ khóa.

3. Bạn sửa tay nhãn một review trong admin, rồi chạy label_data --relabel. Nhãn có bị mất không?

Không. Admin đặt label_source = "manual", và label_reviews loại các review đó bằng .exclude(label_source="manual").

4. Vì sao meta.updatedAt phải đổi sang giờ Việt Nam trước khi lấy ngày?

Database lưu giờ UTC. Lần cào xong lúc 03:00 sáng 6/11 giờ VN là 20:00 ngày 5/11 UTC — lấy ngày thẳng sẽ ra 5/11, sai một ngày. (Test test_updated_at_from_latest_finished_run.)

5. Bài tập: thêm cờ --app <appId> cho sample_labels để chỉ in review của một app.

Gợi ý: parser.add_argument("--app"), rồi trong handle nếu options["app"] có giá trị thì thêm .filter(app_id=...) vào truy vấn labeled_ids. Viết test trước: 2 app, mỗi app 2 review, --app một app → chỉ thấy appId đó.
